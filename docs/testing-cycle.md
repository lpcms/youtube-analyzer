# Регламент тестирования

Девять этапов. Идти по порядку, останавливаться на первом упавшем: дефект дешевле
поймать на раннем этапе. Прогон автоматизирован скиллом `test-cycle`.

| №   | Этап                 | Команда                                                     | Проходит, когда                                                         |
| --- | -------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| 1   | Статический анализ   | `npm run format:check`, `npm run lint`, `npm run typecheck` | Ноль ошибок, без `eslint-disable` и `any`                               |
| 2   | Модульные тесты      | `npm test`                                                  | Зелено; новая бизнес-логика покрыта                                     |
| 3   | Интеграционные тесты | `npm test`                                                  | Зелено; YouTube API замокан, БД — `db/test.db`                          |
| 4   | E2E                  | `npm run test:e2e`                                          | Критический сценарий проходит целиком                                   |
| 5   | Производительность   | `npm run build`, `npm run analyze`                          | First Load JS не вырос без причины; Excel-библиотека вне первого экрана |
| 6   | SEO и доступность    | axe внутри E2E                                              | Ноль нарушений axe; таблица и форма доступны с клавиатуры               |
| 7   | Безопасность         | `npm audit`, `npm run build` + `npm run check:key`          | Ноль уязвимостей; значения ключа API нет в клиентском бандле            |
| 8   | Нагрузочное          | k6 по прод-сборке                                           | Актуально перед деплоем                                                 |
| 9   | UAT                  | Вручную по `tz.txt`                                         | Список расхождений с ТЗ пуст                                            |

## Этап 7 подробнее

**Ищется значение ключа, а не имя переменной.** Имя встречается в бандле
законно: сообщение «проверьте YOUTUBE_API_KEY в файле .env» показывается
пользователю, и переменную в нём надо назвать. Утечка — это когда наружу
уходит сам ключ, и ловить надо именно её. Проверку делает
`scripts/check-bundle-key.mjs`, а сам сканер проверен тестом на подложенной
утечке: сканер, который никогда ничего не находит, хуже отсутствующего.

Проверка требует собранного проекта и без него отказывается работать,
а не печатает «ок»: молчаливое согласие на пустом месте — худший вид зелёного.

**Уязвимости лечатся `overrides`, а не `npm audit fix --force`.** Тот предлагает
откатить `prisma` с 7.10.0 на 6.19.3 и `exceljs` с 4.4.0 на 3.4.0 — мажорные
откаты, ломающие проект ради чужих транзитивных зависимостей. Правильный ход —
поднять нижнюю границу самой уязвимой библиотеки в `overrides` package.json.

## Уровни тестов

Этапы 2–4 задают уровни, которыми оперируют скиллы `decompose` и `plan-phase`:

- **этап 2 — модульные**: чистые функции без окружения (разбор адреса канала,
  вирусность, форматирование длительности и даты, определение Shorts);
- **этап 3 — интеграционные**: React Testing Library плюс настоящая SQLite,
  сетевые вызовы через MSW;
- **этап 4 — E2E**: Playwright по собранному приложению, ответы YouTube API
  перехватываются через `page.route`.

## Критический сценарий E2E

Ввод адреса канала → выбор количества и типов (Video / Shorts) → «Начать» →
таблица с данными → сортировка по просмотрам → переход на вторую страницу →
«Скачать таблицу» → файл скачался и открывается → возврат на главную → канал
виден в истории → открытие из истории даёт ту же таблицу без обращения к API.

## Что в тестах запрещено

- Ходить в настоящий YouTube Data API — трата квоты и зависимость от чужих правок
  на канале.
- Гонять тесты по `dev.db` — см. скилл `db-fixtures`.
- Писать снимки в настоящую папку `history/`: тесты работают во временном каталоге.
- Вычислять ожидаемое значение той же функцией, которую тест проверяет.
