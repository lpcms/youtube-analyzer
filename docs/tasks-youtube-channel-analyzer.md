### T-02: Данные выгрузки сохраняются в SQLite

**Тип:** инфраструктурная
**Зачем:** разблокирует историю, серверную сортировку и пагинацию — всё остальное хранит данные здесь; ряд наблюдений закладывается сразу, потому что прикрутить его позже значит переливать все накопленные данные
**Зависит от:** T-01
**Затрагивает:** db
**Источник:** PRD «В скоупе → Выгрузка» и «История каналов», п.8 ТЗ, анализ 3.6

**Готово, когда:**

- [ ] В схеме Prisma есть модели `Channel`, `Video`, `FetchRun` и `VideoStat`
- [ ] `Channel` опознаётся по идентификатору `UC…` как по первичному ключу и хранит
      название, `@handle`, ссылку на аватар и дату последней выгрузки
- [ ] `Video` хранит неизменное: идентификатор, тип, длительность в секундах целым
      числом, дату публикации в UTC, заголовок и описание
- [ ] `VideoStat` хранит изменчивое: просмотры, лайки, комментарии с допустимым `null`
      и вирусность, по строке на видео в каждой выгрузке
- [ ] `FetchRun` описывает одну выгрузку: канал, время начала и конца, статус,
      прогресс, параметры запроса и путь к снимку
- [ ] Пара «видео + выгрузка» уникальна: повторная запись статистики за ту же
      выгрузку не создаёт второй строки
- [ ] Прежние снимки не затираются: две выгрузки одного канала дают два `FetchRun`
      и два набора `VideoStat`
- [ ] Удаление канала уводит за собой его видео, выгрузки и статистику,
      висячих строк не остаётся
- [ ] Миграция создана и применяется командой `prisma migrate deploy`
- [ ] Интеграционные тесты идут по `db/test.db`, а не по `dev.db`
- [ ] `resetDb()` чистит базу перед каждым тестом в порядке от зависимых
      к справочникам: статистика → выгрузки → видео → каналы
- [ ] Фабрики `makeChannel()`, `makeVideo()`, `makeShort()`, `makeFetchRun()`
      и `makeVideoStat()` возвращают созданные объекты и допускают переопределение
      любого поля

**Тест-кейсы:**

- unit: `makeVideo()` без аргументов даёт видео с валидным 11-символьным идентификатором
- интеграционный: два теста подряд, каждый создающий канал, не мешают друг другу
- интеграционный: две выгрузки одного канала сохраняются как два набора статистики

### T-03: Адрес канала приводится к идентификатору канала

**Тип:** инфраструктурная
**Зачем:** все формы адреса из ТЗ должны вести к одному каналу, иначе выгрузка не начнётся
**Зависит от:** T-01
**Затрагивает:** youtube, form
**Источник:** PRD «Критерии готовности» 1–3, п.2 ТЗ, анализ 2.1

**Готово, когда:**

- [ ] Адреса `youtube.com/@handle`, `youtube.com/channel/UC…`, `youtube.com/c/Name`,
      `youtube.com/user/Name` распознаются, с `https://`, без него и с `www.`
- [ ] Хвосты `/videos`, `/shorts`, `/featured`, `/streams` и строка запроса отбрасываются
- [ ] Адрес не с домена youtube.com отклоняется как невалидный
- [ ] Распознанный адрес превращается в идентификатор канала и плейлист загрузок
      через `channels.list`
- [ ] Адрес вида `/c/Name` разрешается фоллбэком через `search.list`, и в логе видно,
      что вызов стоил 100 единиц квоты
- [ ] Несуществующий канал даёт результат «канал не найден», а не исключение
- [ ] Ключ API читается из `YOUTUBE_API_KEY` и используется только в серверном коде

**Тест-кейсы:**

- unit: разбор адреса — таблица из всех поддерживаемых форм и трёх заведомо неверных
- интеграционный: `@handle` разрешается в идентификатор канала на замоканном ответе API
- интеграционный: несуществующий канал даёт «канал не найден»

### T-05: Тип Video или Shorts виден в таблице

**Тип:** пользовательская
**Зачем:** главный технический риск проекта — API типа не сообщает, а вся фильтрация из ТЗ построена на нём
**Зависит от:** T-04
**Затрагивает:** youtube, table
**Источник:** PRD «Технические ограничения», п.3 ТЗ, анализ 3.1

**Готово, когда:**

- [ ] Длительность приходит в ISO 8601 и хранится в секундах целым числом
- [ ] Видео длительностью более 180 секунд получает тип Video без дополнительных запросов
- [ ] Видео длительностью 180 секунд и менее проверяется запросом к
      `youtube.com/shorts/<id>`: страница без редиректа — Shorts, редирект на
      `/watch` — Video
- [ ] Проверка кандидатов выполняется пакетно и не расходует квоту YouTube API
- [ ] В таблице есть столбец Тип со значением Video или Shorts
- [ ] Недоступность проверки не роняет выгрузку: тип определяется по длительности
      и помечается как предположительный

**Тест-кейсы:**

- unit: разбор длительности — `PT45S`, `PT1M30S`, `PT1H2M3S`, `P1DT2H`
- unit: кандидат в Shorts определяется по порогу 180 секунд включительно
- интеграционный: короткое видео с редиректом на `/watch` получает тип Video
- e2e: в таблице присутствуют строки обоих типов

### T-07: Количество и типы управляют составом выгрузки

**Тип:** пользовательская
**Зачем:** закрывает п.2 ТЗ — пользователь просит ровно то количество и те типы, которые ему нужны
**Зависит от:** T-06
**Затрагивает:** form, youtube
**Источник:** PRD «Критерии готовности» 6–9, п.2 ТЗ, анализ 3.2

**Готово, когда:**

- [ ] В форме есть поле количества и галочки Video и Shorts
- [ ] Обе галочки включены при первой загрузке страницы

### T-11: Вирусность посчитана и выведена

**Тип:** пользовательская
**Зачем:** главная аналитическая ценность сервиса — ради неё таблица и собирается
**Зависит от:** T-10
**Затрагивает:** virality, db
**Источник:** PRD «В скоупе → Вирусность», «Критерии готовности» 16–17, п.3 ТЗ, анализ 3.3

**Готово, когда:**

- [ ] Вирусность считается по формуле
      `round(10 × (0,6 × ER / ER_медиана + 0,4 × просмотры / просмотры_медиана), 1)`,
      где `ER = (лайки + 2 × комментарии) / просмотры`
- [ ] Медианы считаются по всей выгрузке, отдельно для Video и отдельно для Shorts
- [ ] Вирусность медианного видео своего типа равна 10,0 ± 0,1
- [ ] Значение ограничено сверху числом 100
- [ ] Видео с `null` в лайках или комментариях получает «н/д» и в медиану не входит
- [ ] Видео с нулевыми просмотрами получает «н/д»
- [ ] Расчёт выполняется один раз по завершении выгрузки, а не при отрисовке страницы
- [ ] Выгрузка из одного видео не падает: единственное видео своего типа
      получает вирусность 10,0

**Тест-кейсы:**

- unit: вирусность на наборе из пяти видео с вручную посчитанными ожидаемыми числами
- unit: `null` в счётчиках и нулевые просмотры дают «н/д»
- unit: медиана по Shorts не смешивается с медианой по Video
- интеграционный: после выгрузки значения вирусности сохранены в БД
- e2e: колонка Вирусность заполнена для всех строк с полной статистикой

- [ ] Свежие метрики пишутся новым снимком, прежние снимки канала сохраняются

### T-21: Две выгрузки канала сравниваются между собой

**Тип:** пользовательская
**Зачем:** ради динамики и копится ряд снимков — без сравнения он остаётся мёртвым грузом
**Зависит от:** T-19
**Затрагивает:** db, table, ui
**Источник:** PRD «В скоупе → История каналов», критерии 30–31

**Готово, когда:**

- [ ] Прирост показан и абсолютным числом, и долей от прежнего значения

## Вопросы к PRD

1. **Размер страницы таблицы (T-13).** В ТЗ не задан. Предлагаю 50 по умолчанию
   с выбором из 25 / 50 / 100.
2. **Предположительный тип (T-05).** Если подтверждение через `/shorts/<id>`
   недоступно, тип определяется только по длительности. Помечать такие строки
   в интерфейсе или молча доверять длительности?
   Вопрос 2 решается в фазе 2, вопрос 1 — в фазе 3.

**Решено 2026-09-21:** история хранит несколько снимков канала за разные даты,
прежние не затираются (T-02, T-15, T-21). Предел на число снимков и файлов
в `history/` не вводится — чистка только по явному удалению канала.

**Решено 2026-09-21:** отдельной кнопки «Обновить» не будет. «Начать» всегда идёт
в YouTube и обновляет данные, чтение без обращения к API — это выбор канала
из истории (T-19). Устаревание кэша по времени не вводится.
