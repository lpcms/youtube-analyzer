# План: Анализатор видео YouTube-канала

**Задачи:** `docs/tasks-youtube-channel-analyzer.md`
**PRD:** `docs/prd-youtube-channel-analyzer.md`
**Дата:** 2026-09-21

Шесть фаз. После каждой сервис запускается и делает меньше, но делает исправно.

## Фаза 1: Сквозной путь

**Цель:** вставив адрес канала, пользователь получает таблицу его последних видео.
Проверяет, что вся цепочка «форма → YouTube API → SQLite → таблица» собирается,
до того как в неё вложена основная работа.

**Задачи:** T-01, T-02, T-03, T-04
**Тесты фазы:** модульные — разбор адреса канала; интеграционные — разрешение
канала на замоканном API, запись выгрузки в БД; E2E — ввод адреса даёт таблицу
из 10 строк с рабочей ссылкой.
**Готова, когда:** на чистой машине после `npm install` и заполненного `.env`
адрес реального канала даёт таблицу из 10 строк со ссылкой, просмотрами и датой,
а `npm run verify` зелёный.

## Фаза 2: Выгрузка канала целиком

**Цель:** сервис умеет выгрузить весь канал или заданное количество видео нужных
типов и показывает, как идёт дело.

**Задачи:** T-05, T-06, T-07, T-08

T-05 стоит первой намеренно: определение Shorts — единственное место, где решение
неизвестно заранее и опирается на неофициальное поведение YouTube. Если эвристика
не выдержит проверки, это выяснится на второй неделе, а не на восьмой, и переделка
затронет только эту задачу. Вся фильтрация по типам (T-07) на ней стоит.

**Тесты фазы:** модульные — разбор длительности ISO 8601, порог Shorts, разбиение
на пакеты по 50, отбор N элементов выбранных типов, переходы статуса задания;
интеграционные — постраничный обход даёт 137 уникальных строк, запрос 50 Shorts
даёт 50 Shorts, прогресс задания растёт; E2E — в таблице строки обоих типов,
во время выгрузки виден прогресс.
**Готова, когда:** канал больше 50 видео выгружается целиком без дублей и пропусков,
запрос «50 Shorts» даёт ровно 50 строк типа Shorts, во время выгрузки виден прогресс
и кнопка «Начать» заблокирована.

## Фаза 3: Полная таблица

**Цель:** таблица соответствует п.3 и п.4 ТЗ — все колонки, вирусность, сортировка,
страницы. Форма перестаёт пропускать мусор.

**Задачи:** T-09, T-10, T-11, T-12, T-13
**Тесты фазы:** модульные — zod-схема запроса, форматирование длительности, даты
и счётчиков, вирусность на вручную посчитанном наборе, сортировка с `null`, расчёт
числа страниц; интеграционные — описание выводится как текст, сортировка и вторая
страница читаются из БД; E2E — девять колонок, сортировка по просмотрам,
переход на вторую страницу с сохранением сортировки.
**Готова, когда:** таблица показывает девять колонок в форматах из ТЗ, вирусность
посчитана отдельно по Video и Shorts, сортировка и пагинация работают по всей
выгрузке, невалидный ввод выгрузку не запускает.

## Фаза 4: Экспорт и устойчивость

**Цель:** результат можно унести в Excel, повторная выгрузка обновляет канал вместо
того чтобы его дублировать, а отказ API не выглядит поломкой сервиса.

**Задачи:** T-14, T-15, T-16
**Тесты фазы:** модульные — имя файла выгрузки, слияние свежей выгрузки
с сохранённой, разбор ошибки квоты; интеграционные — книга `.xlsx` с ожидаемыми
заголовками и числом строк, повторная выгрузка оставляет одну запись канала,
ошибка 403 на второй странице сохраняет первую; E2E — скачивание непустого `.xlsx`,
повторное «Начать» меняет дату выгрузки, исчерпанная квота показывает сообщение
и частичную таблицу.
**Готова, когда:** «Скачать таблицу» отдаёт `.xlsx` со всеми строками в порядке
сортировки, повторное «Начать» обновляет канал без дублей, исчерпанная квота даёт
сообщение и частичный результат вместо пятисотки.

## Фаза 5: История каналов

**Цель:** вернуться к уже проанализированному каналу можно мгновенно и без расхода
квоты, а на диске остаётся архив снимков, открываемый вне сервиса.

**Задачи:** T-19, T-20

Фаза стоит после экспорта не случайно: список истории показывает ту же таблицу,
что и свежая выгрузка (T-13), обновление канала без дублей уже решено в T-15,
а снимок переиспользует генератор книги из T-14 вместо того чтобы заводить второй.

Источник правды — SQLite, сопоставление каналов по `channelId`. Папка `history/` —
архив снимков, а не хранилище: критерий «удаление `history/` не ломает сервис»
стоит в T-20 именно для того, чтобы эта зависимость не появилась незаметно.

**Тесты фазы:** модульные — сборка строки списка, безопасное имя файла из названия
канала с `/`, эмодзи и кириллицей; интеграционные — открытие из истории не делает
ни одного вызова API, удаление канала не задевает соседний, снимок содержит
ожидаемое число строк; E2E — выгрузка → возврат на главную → открытие из списка
даёт ту же таблицу, удалённая папка `history/` не мешает.
**Готова, когда:** ранее выгруженные каналы перечислены на главной с названием,
счётчиками и датой, открытие любого из них даёт полную таблицу без единого
обращения к YouTube, удаление записи убирает её видео и снимок, а каждая выгрузка
оставляет файл в `history/`.

## Фаза 6: Приёмка

**Цель:** сервис принят по регламенту и по ТЗ.

**Задачи:** T-17, T-18

README пишется последней задачей проекта намеренно: до приёмки состав команд
и возможностей ещё меняется, и написанная раньше документация устареет быстрее,
чем будет дочитана.

**Тесты фазы:** этапы 1–7 регламента `docs/testing-cycle.md` целиком, axe в E2E,
проверка отсутствия ключа в клиентском бандле, проверка, что все упомянутые
в README команды существуют в `package.json`, UAT по `tz.txt`.
**Готова, когда:** таблица «этап → статус» заполнена без падений, список расхождений
с ТЗ пуст с учётом раздела «Отступления от ТЗ» в PRD, а проект разворачивается
по README с нуля.

## Не входит в план

Ничего из `docs/tasks-*.md` не отложено: все двадцать задач распределены по фазам.

Отложено сознательно на уровне PRD (раздел «Не в скоупе»): сравнение каналов,
графики динамики, история метрик во времени, анализ комментариев и обложек,
развёртывание. Причина — сервис личный и запускается локально, эти возможности
не следуют из ТЗ.
