# Регламент тестирования youtube_analyzer

Девять этапов из `docs/testing-cycle.md`. Если в аргументах указан номер — выполнить
только этот этап. Иначе идти по порядку и **останавливаться на первом упавшем**: смысл
регламента в том, что дефект дешевле поймать на раннем этапе.

Итог оформить таблицей «этап → статус → что сломалось».

## 1. Статический анализ и линтинг

```
npm run format:check
npm run lint
npm run typecheck
```

Падение `format:check` чинится `npm run format` — это не дефект, а расхождение форматирования.
Ошибки типов и линта чинить по существу, не глушить `eslint-disable` и `any`.

## 2. Модульное тестирование

```
npm test
```

Проверить, что новая бизнес-логика покрыта. Приоритет покрытия: разбор адреса канала
во всех его формах (`/@handle`, `/channel/UC...`, `/c/...`, `/user/...`), расчёт
вирусности, разбор длительности ISO 8601 (`PT1M30S`) и её форматирование, определение
Shorts против обычного видео, форматирование даты в `2026-09-21 14:21`.
Покрытие смотреть через `npm run test:coverage`.

## 3. Интеграционное тестирование

Те же `npm test` — интеграционные тесты живут рядом с unit-овыми, но рендерят страницы
и формы через React Testing Library, а обращения к YouTube Data API мокают через MSW.
Проверять: форму запроса и её валидацию, постраничную выгрузку канала, запись
результата в SQLite и чтение из кэша, поведение при исчерпанной квоте.

**Ни один тест не ходит в настоящий YouTube API** — это трата квоты и зависимость
от чужих правок на канале.

## 4. E2E

```
npm run test:e2e
```

Playwright сам поднимет дев-сервер, ответы API перехватываются через `page.route`.
Критический сценарий: ввод адреса канала → выбор количества и типов → «Начать» →
таблица с данными → сортировка по просмотрам → переход на вторую страницу →
«Скачать таблицу» → файл скачался и открывается.

## 5. Производительность и Core Web Vitals

```
npm run build
npm run analyze
```

Смотреть размер First Load JS по маршрутам и отчёт анализатора бандла.
Библиотеку генерации Excel подключать динамически — она нужна только по клику
на «Скачать таблицу» и не должна попадать в первый экран. Таблица на несколько
тысяч строк проверяется на отзывчивость сортировки и переключения страниц.
Lighthouse — вручную по собранному прод-билду (`npm run start`).

## 6. SEO и доступность

Проверка axe встроена в E2E (`tests/e2e/smoke.spec.ts`). При добавлении экрана —
добавить туда его проверку. Смотреть: семантику таблицы (`th` с `scope`,
`aria-sort` у сортируемых колонок), связь полей формы с подписями и текстами
ошибок, работу с клавиатуры, контрастность, метатеги в `layout.tsx`.

## 7. Безопасность

```
npm audit
```

Уязвимостей быть не должно. Кроме аудита проверить: ключ YouTube API живёт только
на сервере и не попадает в клиентский бандл (переменная **без** префикса
`NEXT_PUBLIC_`); адрес канала и все параметры запроса проходят через zod-схему;
описание видео выводится как текст, а не как HTML; заголовки безопасности
из `next.config.ts` реально отдаются.

## 8. Нагрузочное тестирование

k6 — внешний бинарник, ставится отдельно (`winget install k6`). Гонять по
серверным действиям и API-роутам на прод-сборке с замоканным YouTube API.
Актуально перед деплоем.

## 9. UAT

Ручная проверка по пунктам `tz.txt`: каждое поле формы и каждый столбец таблицы
из ТЗ должны существовать и работать. Результат — список расхождений с ТЗ.
Сознательные отступления от ТЗ расхождением не считаются, если они записаны
в разделе «Отступления от ТЗ» в PRD.
