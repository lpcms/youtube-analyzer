# Задачи в GitHub

Последнее звено цепочки: [[prd]] → [[decompose]] → [[plan-phase]] → issues.
Скилл отвечает за issue от её создания до закрытия, а не только за выгрузку плана.

Вход: `docs/plan-<фича>.md` (или путь в `$ARGUMENTS`) и файл задач
`docs/tasks-<фича>.md`, на который тот ссылается.
Репозиторий проекта — `lpcms/youtube_analyzer` (приватный).

Язык issues и milestones — **русский**: заголовки, тела, критерии готовности.
Английскими остаются только метки и имена файлов.

## Предварительные условия

Нужен доступ к GitHub API. Годится любой из двух:

- `gh` CLI с авторизацией (`gh auth status` показывает активный аккаунт);
- Personal Access Token в переменной окружения `GITHUB_TOKEN` — тогда работать
  через REST API напрямую. Нужные права на этот репозиторий:
  `Issues: read and write` (создание и отметка), `Contents: read and write`
  (push веток), `Pull requests: read and write` (PR). Права выдаются по
  отдельности: с одним лишь `Issues` создание PR падает с 403.

Deploy key репозитория для этого **не годится** — он даёт доступ только
к git-транспорту, но не к GitHub API. Если нет ни `gh`, ни токена — остановиться
и сказать об этом, а не пытаться обойти.

Перед созданием проверить, что бэклог не заводится повторно: получить список
issues (`--state all`, лимит 200) и список milestones. Совпадения по заголовкам
не дублировать.

### Вызовы через PAT

Когда `gh` нет, а `GITHUB_TOKEN` есть, обращаться к API так (PowerShell):

```powershell
$h = @{ Authorization = "Bearer $env:GITHUB_TOKEN"; Accept = "application/vnd.github+json" }
$base = "https://api.github.com/repos/lpcms/youtube_analyzer"

# milestone
$body = @{ title = "Фаза 1: название"; description = "цель фазы" } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$base/milestones" -Headers $h -Body $body -ContentType "application/json"

# issue
$body = @{ title = "..."; body = "..."; milestone = 1; labels = @("feature","table") } | ConvertTo-Json -Compress -Depth 5
Invoke-RestMethod -Method Post -Uri "$base/issues" -Headers $h -Body $body -ContentType "application/json"
```

Тело issue содержит кириллицу и переносы строк — собирать его через `ConvertTo-Json`,
а не склейкой строк, иначе экранирование поедет. Токен нигде не печатать:
ни в описании команды, ни в выводе, ни в файлах репозитория.

## Порядок действий

1. Прочитать план и файл задач.
2. Для каждой фазы создать milestone «Фаза N: название» с целью фазы в описании.
3. Создать недостающие метки (см. ниже) — **до** создания issues, иначе запрос упадёт.
4. Для каждой задачи фазы создать issue с привязкой к milestone.
5. В конце вывести таблицу: задача → номер issue → milestone.

## Формат issue

**Title** — результат из задачи одной строкой, без префикса `T-NN` и без `[ ]`.

**Body** собирается из полей задачи:

```
Задача: T-<номер> из docs/tasks-<фича>.md

<Зачем — одна фраза>

**Готово, когда:**
- [ ] критерий
- [ ] критерий

**Тест-кейсы:**
- unit: ...
- интеграционный: ...
- e2e: ...

**Зависит от:** #<номера созданных ранее issues> или «ничего»
**Затрагивает:** зоны кода
```

**Метки.** По типу задачи: `feature` или `infra`. По зоне кода:

| Метка      | Зона                                                      |
| ---------- | --------------------------------------------------------- |
| `form`     | форма запроса: адрес канала, количество, чекбоксы, валидация |
| `youtube`  | обращения к YouTube Data API, разбор ответов, квота, лимиты |
| `table`    | таблица результатов: колонки, сортировка, пагинация       |
| `virality` | расчёт вирусности                                          |
| `export`   | выгрузка в Excel                                           |
| `db`       | SQLite, схема Prisma, миграции, кэш выгрузок              |
| `ui`       | оформление, состояния загрузки и ошибок, адаптивность     |

## Правила создания

- Не выдумывать задачи, которых нет в плане, и не менять формулировки критериев:
  issue должна быть дословно проверяема против `docs/tasks-*.md`.
- Зависимости проставлять ссылками на реальные номера issues, поэтому создавать
  их в порядке фаз, а внутри фазы — в порядке зависимостей.
- Если задача зависит от чего-то, чего нет в плане, — остановиться и сообщить,
  это ошибка планирования, а не повод импровизировать.

# Жизненный цикл issue

Бэклог, в котором ничего не меняется по ходу работы, бесполезен: со стороны он
выглядит так, будто работа не идёт. Поэтому issue обновляется **в тот же заход**,
что и код.

## Два признака, которые нельзя путать

| Признак | Что означает | Когда ставится |
| ------- | ------------ | -------------- |
| `- [x]` у критерия | критерий **проверен**, есть доказательство | сразу, как доказательство появилось |
| issue закрыта | работа **в `main`** | при мерже PR |

Разделение важное: код может быть готов и проверен, но ещё не влит. Тогда
у issue отмечены все критерии, а сама она открыта — и это честная картина,
а не незакрытый хвост.

## Когда отмечать критерий

Критерий отмечается, только когда выполнены **оба** условия:

1. `npm run verify` зелёный (плюс `test:e2e`, если критерий про e2e);
2. у критерия есть **названное доказательство** — имя теста, вывод команды
   или описанная ручная проверка.

«Код написан» и «выглядит готовым» доказательством не считаются. Критерий,
для которого доказательство не придумывается, **не отмечать** — это сигнал,
что он либо не выполнен, либо сформулирован непроверяемо, и об этом нужно
сказать, а не закрасить.

Отмечать по ходу можно и нужно: три из семи отмеченных критериев — это видимый
прогресс. Отмечать оптом «всё разом в конце» — нельзя.

## Как отмечать

Тело issue правится целиком через `PATCH /repos/:owner/:repo/issues/:number`:
берётся текущее тело, в нём построчно `- [ ]` меняется на `- [x]` **только
у проверенных** критериев. Формулировки не трогать — issue должна остаться
дословно сверяемой с `docs/tasks-*.md`.

```powershell
$h = @{ Authorization = "Bearer $env:GITHUB_TOKEN"; Accept = "application/vnd.github+json" }
$base = "https://api.github.com/repos/lpcms/youtube_analyzer"

$issue = Invoke-RestMethod -Uri "$base/issues/7" -Headers $h
$body = $issue.body -replace '(?m)^- \[ \] (Адрес не с домена)', '- [x] $1'
$payload = @{ body = $body } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Patch -Uri "$base/issues/7" -Headers $h -Body $payload -ContentType "application/json; charset=utf-8"
```

Следом — комментарий с таблицей «критерий → чем подтверждён». Он и есть
аудиторский след: через месяц по нему видно, почему галочка стоит.

```
## Проверено

| Критерий | Чем подтверждён |
| --- | --- |
| Хвосты /videos и /shorts отбрасываются | unit `разбор адреса: хвосты пути` |
| Несуществующий канал даёт «канал не найден» | интеграционный `канал не найден` |

`npm run verify` зелёный, `npm run test:e2e` — 3 passed.
Ветка `feat/7-channel-url`, коммит abc1234.
```

## Закрытие

`Closes #N` в теле PR закрывает issue автоматически — **но только при мерже
в ветку по умолчанию**. При стопке веток (PR с базой не `main`, а другой рабочей
веткой) ключевое слово не сработает.

### Ловушка: удаление базовой ветки закрывает PR

**Удаление ветки, которая служит базой открытому PR, закрывает этот PR — без
мержа.** Не перенацеливает на `main`, а именно закрывает. Проверено на практике:
после мержа PR-родителя его ветка была удалена, и дочерний PR закрылся
неслитым, а внук смержился в промежуточную ветку вместо `main`. Работа
не потерялась, но в `main` не попала, а задачи оказались закрыты преждевременно.

GitHub действительно умеет перенацеливать дочерний PR при мерже родителя,
но это срабатывает не всегда, и **проверять надо до удаления, а не после**.

### Порядок мержа стопки

1. Смержить нижний PR (его база — `main`). **Ветку пока не удалять.**
2. Для каждого PR, у которого базой была эта ветка, **перенацелить базу
   на `main`** явным `PATCH /pulls/:number` с `{"base": "main"}`.
3. Убедиться, что после перенацеливания PR остался `open` и `mergeable`.
4. Только теперь удалить ветку смерженного родителя.
5. Повторить для следующего уровня.

Проще и надёжнее — **не строить стопку глубже двух уровней**. Когда задача
зависит от невлитой предыдущей, разумнее дождаться мержа, чем копить стопку:
разбирать её дороже, чем подождать.

Если стопка уже слиплась неправильно — не откатывать историю, а открыть один
PR из уцелевшей ветки в `main`: она содержит все накопленные коммиты, и мерж
применит их разом, ничего не задваивая.

### Проверка после мержа

**После мержа проверить состояние issue и, если она осталась открытой, закрыть
явно**, комментарием со ссылкой на коммит в `main`. Проверять фактом, а не
предположением: запросить содержимое `main` и убедиться, что файлы задачи там.
Закрытая issue при работе, не дошедшей до `main`, — худший исход: бэклог врёт.

```powershell
Invoke-RestMethod -Method Patch -Uri "$base/issues/7" -Headers $h `
  -Body (@{ state = "closed"; state_reason = "completed" } | ConvertTo-Json -Compress) `
  -ContentType "application/json"
```

Issue не закрывается вручную, пока работа не в `main`: закрытая issue означает
«сделано и влито», и нарушать это — значит терять единственный надёжный признак
готовности.

## Чего не делать

- Не отмечать критерий, для которого нет доказательства.
- Не закрывать issue до мержа в `main`.
- Не переписывать формулировки критериев при отметке.
- Не считать `Closes #N` достаточным, когда база PR — не `main`.
- Не удалять ветку, пока на неё смотрит база другого открытого PR.
- Не закрывать задачу, не запросив `main` и не убедившись, что работа там.
- Не откладывать отметку «на потом»: бэклог должен быть верен на любой момент.
