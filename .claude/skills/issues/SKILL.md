# Выгрузка плана в GitHub

Последнее звено цепочки: [[prd]] → [[decompose]] → [[plan-phase]] → issues.

Вход: `docs/plan-<фича>.md` (или путь в `$ARGUMENTS`) и файл задач
`docs/tasks-<фича>.md`, на который тот ссылается.
Репозиторий проекта — `lpcms/youtube_analyzer` (приватный).

Язык issues и milestones — **русский**: заголовки, тела, критерии готовности.
Английскими остаются только метки и имена файлов.

## Предварительные условия

Нужен доступ к GitHub API. Годится любой из двух:

- `gh` CLI с авторизацией (`gh auth status` показывает активный аккаунт);
- Personal Access Token с правом `Issues: read and write` на этот репозиторий,
  в переменной окружения `GITHUB_TOKEN` — тогда работать через REST API напрямую.

Deploy key репозитория для этого **не годится** — он даёт доступ только
к git-транспорту, но не к GitHub API. Если нет ни `gh`, ни токена — остановиться
и сказать об этом, а не пытаться обойти.

Перед созданием проверить, что бэклог не заводится повторно: получить список
issues (`--state all`, лимит 200) и список milestones. Совпадения по заголовкам
не дублировать.

### Вызовы через PAT

Когда `gh` нет, а `GITHUB_TOKEN` есть, обращаться к API так (PowerShell):

```powershell
$h = @{ Authorization = "Bearer $env:GITHUB_TOKEN"; Accept = "application/vnd.github+json" }
$base = "https://api.github.com/repos/lpcms/youtube_analyzer"

# milestone
$body = @{ title = "Фаза 1: название"; description = "цель фазы" } | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$base/milestones" -Headers $h -Body $body -ContentType "application/json"

# issue
$body = @{ title = "..."; body = "..."; milestone = 1; labels = @("feature","table") } | ConvertTo-Json -Compress -Depth 5
Invoke-RestMethod -Method Post -Uri "$base/issues" -Headers $h -Body $body -ContentType "application/json"
```

Тело issue содержит кириллицу и переносы строк — собирать его через `ConvertTo-Json`,
а не склейкой строк, иначе экранирование поедет. Токен нигде не печатать:
ни в описании команды, ни в выводе, ни в файлах репозитория.

## Порядок действий

1. Прочитать план и файл задач.
2. Для каждой фазы создать milestone «Фаза N: название» с целью фазы в описании.
3. Создать недостающие метки (см. ниже) — **до** создания issues, иначе запрос упадёт.
4. Для каждой задачи фазы создать issue с привязкой к milestone.
5. В конце вывести таблицу: задача → номер issue → milestone.

## Формат issue

**Title** — результат из задачи одной строкой, без префикса `T-NN` и без `[ ]`.

**Body** собирается из полей задачи:

```
Задача: T-<номер> из docs/tasks-<фича>.md

<Зачем — одна фраза>

**Готово, когда:**
- [ ] критерий
- [ ] критерий

**Тест-кейсы:**
- unit: ...
- интеграционный: ...
- e2e: ...

**Зависит от:** #<номера созданных ранее issues> или «ничего»
**Затрагивает:** зоны кода
```

**Метки.** По типу задачи: `feature` или `infra`. По зоне кода:

| Метка      | Зона                                                      |
| ---------- | --------------------------------------------------------- |
| `form`     | форма запроса: адрес канала, количество, чекбоксы, валидация |
| `youtube`  | обращения к YouTube Data API, разбор ответов, квота, лимиты |
| `table`    | таблица результатов: колонки, сортировка, пагинация       |
| `virality` | расчёт вирусности                                          |
| `export`   | выгрузка в Excel                                           |
| `db`       | SQLite, схема Prisma, миграции, кэш выгрузок              |
| `ui`       | оформление, состояния загрузки и ошибок, адаптивность     |

## Правила

- Не выдумывать задачи, которых нет в плане, и не менять формулировки критериев:
  issue должна быть дословно проверяема против `docs/tasks-*.md`.
- Зависимости проставлять ссылками на реальные номера issues, поэтому создавать
  их в порядке фаз, а внутри фазы — в порядке зависимостей.
- Если задача зависит от чего-то, чего нет в плане, — остановиться и сообщить,
  это ошибка планирования, а не повод импровизировать.
